# 文件即接口：agent 自动化系统的调度解耦模式
<p class="dg-date">✍️ 2026-08-18</p>
> [!info] 一句话结论
> 多个 agent / 多个 cron 之间不要互相调用，用**约定文件名传递数据**：生产者落盘，消费者按约定路径读。接口即文件，时序解耦、单环断裂可自愈、全程可审计。

## 问题：agent 系统里的"谁叫谁"

一个 AI agent 体系里常见的自动化链：

```
每日探索(agent 会话) → 汇总周报(agent 会话) → 推送给人类
每日备份(shell)     → 算发布差异(python) → 询问人类(agent)
```

天真做法是**互相调用**：探索完"通知"周报，备份完"触发"闸门。但 agent 会话是昂贵、脆弱、有状态的——一旦互相调用，就产生时序耦合（消费者必须等生产者活着跑完）、单点放大（一环挂全链挂）、不可审计（调用链藏在进程里）。

## 模式：文件即接口

每一对"生产者→消费者"约定一个文件路径 + 格式，仅此而已：

| 生产者 | 接口文件 | 消费者 |
|---|---|---|
| 每日探索 worker | `explore-brief.txt`（覆盖写） | 投递 shell（读后直发 IM） |
| 周回顾 worker | `周回顾-2026-W33.md` | 周一推送 cron（按通配找最新） |
| 备份脚本 | `publish-pending.json` | 发布闸门 cron（有货才问人） |

三条设计规则：

1. **生产者只管写**：写到约定路径就算完成任务，不关心谁来读、什么时候读
2. **消费者只管读**：读不到就走兜底逻辑（见下），不追责生产者
3. **文件名即 API**：路径和格式写进双方的 prompt/脚本，是唯一契约

## 为什么它比"互相调用"好

**时序解耦**：周报 cron 在周一 08:30 读周日的产物，隔夜 12 小时——生产者根本不需要在线。这天然支持重试：消费者读失败，下轮再读，文件还在。

**单环断裂可自愈**（实测案例）：某夜周回顾脚本跑的是旧版、没落盘接口文件。次日推送 cron 读不到文件，按 prompt 里的兜底指令——"查明原因并补"——它翻运行日志和 git，**自己重构出周报落盘，照常完成推送**，还顺手修复了旧脚本（git 留痕）。事后人类只在微信收到一条正常周报，事故被静默消化。

**零成本投递分离**：worker（花 token 的 LLM 会话）只写文件；真正推送用 CLI 直发通道（如 `hermes send`），不经过任何模型。**智能多少钱、投递多少钱，账单清清楚楚**。

**全程可审计**：每个接口文件就是数据快照，git 一收，谁在何时产出了什么、消费了什么，全有痕。

## 边界：什么时候不要用

- **需要实时响应**（秒级）：文件轮询太慢，用事件/webhook
- **大流量数据流**：文件系统不是消息队列，别拿它扛吞吐
- **强事务**：没有 exactly-once 语义，重复消费要靠幂等设计兜

## 与业界原则的对照

这本质是调度系统设计里的经典共识——**"when（何时跑）与 how（怎么跑）分离"**——在 LLM agent 场景的具体化：cron 只做哑触发，智能住进 skill，而**层与层之间用文件粘合**。传统微服务用消息总线解耦；单机 agent 体系里，文件系统就是最简单、最可靠的那条总线。

> 经验来自一个真实运转的体系：两层 cron（系统 crontab + agent 框架调度器）、每日/每周 worker、发布审批闸门，事故与自愈均有 git 与日志实证。
